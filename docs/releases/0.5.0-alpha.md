# DashBridge 0.5.0-alpha

This prerelease establishes the new two-board architecture as the only
supported firmware design. It preserves messages, calls, music, contacts,
app-policy setup, and the released iOS Setup GATT v1 contract. It remains an
experimental build, not a verified daily-use adapter.

## What's new since 0.4.3-alpha

- Firmware now has one composition root with portable domain core, narrow
  runtime ports, Bluetooth adapters, bounded protocols, transport, and ESP-IDF
  platform code.
- Board-to-board control uses typed DashLink v2 packets. Encoded call and music
  media stay on the dedicated media link so bulk audio cannot block setup,
  messages, commands, contacts, or health heartbeats.
- Initial iPhone pairing is staged: Dash Messages and notification sharing must
  become ready before Dash Calls is discoverable. The iPhone owns phone-side
  reconnect attempts; the Tesla-facing gateway stays passive, while music and
  phonebook connection attempts are serialized.
- Firmware, build tools, browser setup, tests, and CI support exactly Board A
  and Board B. Retired experimental targets, vendor diagnostic patches,
  milestone notes, and duplicate routing code are no longer active.
- The canonical architecture and USB command guides describe the complete
  current system, including manual setup without the iPhone app.

The [manifest](../../dist/manifest.json) records image sizes, source hashes,
flash addresses, and the pinned ESP-IDF revision. Install A and B from this
same release. Full images flash at `0x0` and may erase Bluetooth bonds and app
choices. Application-only images flash at `0x10000` only when the existing
partition layout is known to match.

## Verification and limits

Both images build with pinned ESP-IDF v5.5.5. Architecture, protocol, bounded
input, call/music audio, reconnect, build-scope, browser, installer-integrity,
and production SDP/configuration checks pass. The iOS Setup GATT v1 contract is
checked against both firmware and companion-app code.

These exact images have **not** been installed and tested end to end with an
iPhone and Tesla. The manifest therefore keeps `hardware_tested: false` for
both. Notification delivery, clear bidirectional call audio, music playback and
controls, phonebook/history sync, and sustained reconnect behavior still need a
parked-car test. Earlier phonebook pulls returned zero records; this release
must not be presented as fixing that until hardware proves it.

Use the [setup guide](../SETUP.md) and the
[parked-car checklist](../../README.md#parked-car-test-checklist). Keep the
existing direct-phone option until the bridge has been verified in your car.
